# دار الهندسة للأنظمة المتطورة

متجر عربي باتجاه RTL مبني بـ Angular 22 مع API خلفي في Node.js. تُقرأ بيانات المنتجات والتصنيفات والعلامات التجارية والمخزون والإعدادات والرسائل من Supabase PostgreSQL. لا يستخدم المتجر كتالوجاً ثابتاً أو SQLite كمصدر بيانات.

## تشغيل محلي

1. انسخ `.env.example` إلى `.env`.
2. أضف `SUPABASE_URL` و`SUPABASE_SERVICE_ROLE_KEY` في `.env`، مع `SESSION_SECRET` و`ADMIN_EMAIL` و`ADMIN_PASSWORD`. مفتاح الخدمة سري ويظل في الخادم فقط.
3. قاعدة production الحالية تحتوي المخطط المنشور بالفعل. لا تعِد تطبيق ملفات migrations عليها من بيئة التطوير.
4. شغّل الواجهة والخادم في نافذتي PowerShell منفصلتين:

```powershell
npm install
npm start
```

```powershell
npm run start:api
```

افتح `http://127.0.0.1:4200`.

عامل انتهاء حجوزات واتساب متوقف افتراضياً محلياً. لا يعمل إلا مع `WHATSAPP_RESERVATION_WORKER_ENABLED=true` وفي `APP_ENV=production` أو `APP_ENV=staging` مع `NODE_ENV=production`. وضع التطوير يمنعه حتى لو كان المفتاح مفعلاً. في الإنتاج خصص خدمة API مراقبة واضبط متغيرات البيئة صراحةً؛ في staging سيُرفض ملف الإعداد إذا أشار إلى مشروع production أو خلط بيانات اعتماد موروثة.

## بيئة staging معزولة

لا ينشئ المشروع مشروع Supabase أو موارد سحابية تلقائياً. جهّز مشروع Supabase منفصلاً للاختبار، ثم جهّز قاعدة staging من ملفات migrations الموجودة بإجراء منفصل ومراجع؛ أوامر المشروع هنا لا تطبق migrations. استخدم بيانات ومنتجاً تجريبياً خاصاً بـ staging فقط.

1. انسخ `.env.staging.example` إلى `.env.staging`.
2. استبدل كل placeholder بـ project ref و`SUPABASE_URL` ومفتاح خدمة وقيم مدير و`SESSION_SECRET` خاصة بـ staging. يجب أن يطابق ref المضبوط عنوان URL وألا يكون `ipegazjnkejasorskdur`.
3. اضبط `STAGING_TEST_PRODUCT_ID` على UUID لمنتج staging نشط ذي مخزون كافٍ. أنشئ هذا المنتج داخل مشروع staging فقط.
4. اترك `WHATSAPP_RESERVATION_WORKER_ENABLED=false` للاختبارات العادية. لتجربة الانتهاء فقط، فعّله في `.env.staging` بعد التأكد من أن المشروع المنفصل يحتوي بيانات disposable؛ يتطلب العامل `NODE_ENV=production` حتى داخل وضع staging.
5. شغّل API باستخدام `npm run start:api:staging`. يجب أن يعرض `/api/health` `environment=staging` وref المشروع المحدد قبل أي اختبار. يفشل التشغيل إذا كان `.env.staging` مفقوداً أو غير مكتمل أو يشير إلى production. لا يستخدم وضع staging قيم Supabase أو مدير موروثة من البيئة أو `.env`.
6. شغّل الواجهة عبر `npm start`، ثم شغّل مجموعة checkout والتزامن: `npm run test:orders:staging -- --suite=checkout --confirm-staging-writes`.
7. بعد تفعيل عامل staging فقط، اختبر الانتظار الفعلي 30 دقيقة: `npm run test:orders:staging -- --suite=expiration --confirm-staging-writes`. مجموعة `all` تجمع الاختبارين. هذه السكربتات تنشئ وتلغي أو تنتظر طلبات staging؛ لا تشغّلها على production.

ملف `.env.staging` مستثنى من Git. لا تنسخ إليه قيمة من `.env`. سكربت الاختبار يرفض ref الإنتاج، ويفرض loopback API، ويتحقق من أن API نفسه يؤكد مشروع staging قبل إنشاء أول طلب.

## مزامنة البيانات وأمانها

- عمليات المنتجات تُنفذ عبر API Node المحمي بجلسة مدير ثم Supabase باستخدام مفتاح الخدمة الموجود بالخادم. لا يتصل المتصفح بالجداول مباشرة.
- إدخال المنتج وتحديث بياناته والكمية وسجل حركة المخزون يتمان داخل دالة PostgreSQL ذرية.
- كل تعديل مخزون يسجل الفرق والكمية بعد التعديل والسبب ووقت التعديل وحساب المدير.
- أرشفة المنتج تغيّر حالته وتاريخ الأرشفة وتحافظ على سجل الطلبات والحركات.
- التصنيفات والعلامات التجارية لها مفاتيح خارجية تمنع حذف سجلات مرتبطة؛ واجهة الإدارة تعرض الأرشفة وإعادة التسمية وإعادة التفعيل.
- سياسات RLS مفعلة ولا تمنح أدوار المتصفح وصولاً مباشراً. الخادم فقط يستخدم `service_role`.
- بقية بيانات الموقع التشغيلية (الحسابات، الفروع، الإعدادات، الرسائل، طلبات السعر والتجار) محفوظة أيضاً في Supabase.
- طلبات الموقع وواتساب تتحقق من السعر والمخزون الحاليين داخل معاملة PostgreSQL، وتحفظ لقطات اسم/SKU/سعر المنتج، وعنوان التوصيل، ورسومه؛ إلغاء الطلب يعيد الكميات إلى المخزون مع سجل حركة.
- إرسال الطلب يستخدم مفتاح UUID ثابتاً للمحاولة وبصمة SHA-256 يحسبها الخادم؛ تكرار المفتاح بنفس التفاصيل يعيد الطلب الأصلي، وإعادة استخدامه لتفاصيل مختلفة تُرفض.
- طلب واتساب يحجز المخزون لمدة 30 دقيقة. خادم API يشغّل مسحاً دورياً للطلبات المنتهية؛ تغيير الحالة يتحقق أيضاً من المهلة ويمنع تنفيذ طلب انتهى حجزه.
- الاستيراد من Excel يعرض معاينة وأخطاء لكل صف، ويضيف المنتجات الجديدة فقط بعد التحقق من تكرار SKU.

## البناء

```powershell
npm run build
```

## ترحيل الطلبات والتوصيل

ترحيل `supabase/migrations/20261119213150_delivery_orders.sql` يضيف حقول التوصيل ومفتاح idempotency وبصمة الطلب ومهلة حجز واتساب، ويهيئ دوال الطلب والإلغاء وانتهاء الحجز. تم تطبيقه بالفعل على مشروع Supabase production وتسجيل الإصدار `20261119213150`؛ لا تعِد تنفيذ SQL لهذا الترحيل على المشروع. لا تمنح `service_role` للمتصفح. أبقِ خادم API عاملاً كي يعالج حجوزات واتساب المنتهية كل دقيقة؛ وعند توقفه ستعالج عند عودته أو عند محاولة تحديث حالة الطلب.

لا تعتمد المنتجات والأسعار على بيانات تجريبية في الواجهة. لإنشاء بيئة Supabase جديدة طبّق ملفات المخطط مرة واحدة بالترتيب. في بيئة الإنتاج الحالية لا تعِد تنفيذ هجراتها. قبل النشر عيّن نطاق `FRONTEND_ORIGIN`، استخدم HTTPS وسرّاً قوياً، وأضف المنتجات الحقيقية من لوحة الإدارة.


## إدارة صور المنتجات

الصور تُرفع من لوحة الإدارة إلى bucket عام باسم `product-images` عبر خادم Node.js المصادق عليه؛ لا يُرسل مفتاح Supabase إلى Angular. يقبل الخادم JPG وPNG وWebP ويتحقق من توقيع محتوى الملف، ويولّد مساراً فريداً داخل `products/{productId}/`. الحقل الحالي `products.image` يخزن رابط الصورة، ولا حاجة إلى عمود جديد. الحذف يمسح المرجع أولاً ولا يحذف كائن Storage إلا إذا كان رابطاً من هذا المشروع، داخل مسار المنتج نفسه، ولا توجد منتجات أخرى تشير إليه. الروابط الخارجية لا تُحذف.

الحد الافتراضي للرفع 5 MiB. يمكن ضبطه عبر `PRODUCT_IMAGE_MAX_BYTES` (حتى 20 MiB). واجهة الإدارة تعرض معاينة وتقدم الرفع؛ تعطل رفع البديل يُبقي المرجع الحالي. قيمة الصورة الفارغة في المخطط الحالي تُخزن كسلسلة فارغة لأن العمود `products.image` غير قابل لـNULL.
